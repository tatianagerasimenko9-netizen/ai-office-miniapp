# ОФІС AI АГЕНТІВ

Дата старту: 04.05.2026
Статус: активний робочий журнал.

## Мета
- Побудувати реальний AI-офіс агентів для торгівлі у Telegram.
- Фіксувати всі ідеї, промпти, рішення і кроки реалізації.
- Брати в роботу найсильніші ідеї, перевіряти на ризик і практичність.

## Незмінні правила
- Мова: українська, проста і чітка.
- Без команди `пиши` код не змінюємо.
- `TARGET_BLOCK_ALL_SIGNALS=False` лишається (блок "Ціль дня" інформаційний).
- Автозбереження: кожні 10 хвилин під час роботи.

## Архітектурний принцип офісу
- Швидкий контур: рішення по сигналу без затримок (GO/HOLD/SKIP).
- Аналітичний контур: обговорення агентами після рішення (розбір, покращення).
- Ролі агентів: на базі твоїх 8 ролей + диспетчер (керівник).

## Що вже зафіксовано
1. Папка `Офіс` створена в пам'яті бота.
2. Узгоджено, що "Ціль дня" не блокує сигнали.
3. Додано пріоритет: аналіз недобору руху після TP2/TP3 (кейс `BABYUSDT`).
4. Узгоджено ціль: зробити "реальний офіс AI агентів" у Telegram.

## Поточний список перевірок/покращень (v1)
1. Перевірити консистентність метрик `Сигналів` і `Підтверджених входів`.
2. Перевірити логіку `loss_streak` (інкремент/скидання/перенесення між днями).
3. Розкласти серійні SL по патернах (сесія, тип, джерело, режим ринку).
4. Окремо оцінити SMC funnel: сигнал -> вхід -> TP1/TP2/SL.
5. Додати блок недобору руху: `MFE` після TP1/TP2.
6. Для SMC впровадити runner-супровід без явного TP3 у сигналі.
7. Залишити потік сигналів активним, підкручувати точково лише слабкі місця.

## Журнал обговорення

- Вирішено: фіксувати нові ідеї по 5 ШІ-ролях і відбирати найсильніші в роботу.

  - рішення: взяти / відкласти / відхилити.

## Аналіз ідеї #1 (Perplexity) — Trading AI Office
Дата: 04.05.2026

### Суть ідеї
- Зробити Telegram "trading floor", де 6 агентів обговорюють кожен сигнал.
- Є диспетчер (Alice), голосування агентів, консенсус і фінальний вердикт.
- Додати shared memory (Redis/Postgres), task tracking і Mini App dashboard.

### Сильні сторони (беремо в роботу)
1. Розподіл ролей і рішень по спеціалізації (ризик, квант, сесія, red team).
2. Прозорий вердикт по кожному сигналу (чому вхід/чому пропуск).
3. Shared memory для історії рішень, що дає якісні post-trade розбори.
4. Ідея трекати ефективність агентів окремо (корисно для тюнінгу правил).
5. Mini App як центр моніторингу (статус, навантаження, результативність).

### Слабкі місця і ризики (критично)
1. "90 сек дебати" перед входом неприйнятні для скальпу (втрата точки входу).
2. "Guaranteed $100/day" - нереалістично і небезпечно для risk-політики.
3. Повністю LLM-орієнтоване рішення може давати нестабільні відповіді в live.
4. Багатоагентна розмова може створити шум замість дисципліни без жорсткого протоколу.

### Рішення по ідеї
- Статус: **ВЗЯТИ ЧАСТКОВО (ядро)**.
- Не беремо: довгі дебати перед входом, обіцянки гарантованого доходу.
- Беремо: ролі, диспетчер, спільну пам'ять, консенсус-движок, dashboard.

### Як адаптуємо під твого бота
1. Швидкий контур (execution): 1-3 секунди, deterministic правила + короткий AI-висновок.
2. Аналітичний контур (office room): детальна дискусія вже після вердикту.
3. Для SMC/PREPUMP: обов'язково додати метрики недобору (`MFE after TP2`) і runner-логіку.

### MVP план (реалістичний)
1. Старт без Mini App: Telegram room + dispatcher + 4 ключові агенти.
2. Далі shared memory (Redis/Postgres) + історія рішень по `signal_id`.
3. Потім dashboard (Mini App) для live-метрик і оцінки агентів.

## Аналіз ідеї #2 (CHATGPT) — "AI Office як система рішень"
Дата: 04.05.2026

### Суть ідеї
- AI-офіс не генерує сигнали сам, а фільтрує сигнали базової стратегії.
- Ролі: Dispatcher -> Analyst -> Risk -> Strategist -> Logger.
- Фокус на реальній "фондовій" структурі: рішення, ризик, дисципліна, журнал.

### Сильні сторони (беремо в роботу)
1. Дуже правильний принцип: AI = decision-support, а не "чарівний автотрейдер".
2. Чіткий поділ: стратегія генерує, агенти фільтрують і ранжують якість.
3. Жорсткий пріоритет Risk Manager як стоп-кран проти зливу.
4. Сильна ідея Logger: повний розбір "сигнал -> рішення -> результат".
5. Мінімалістичний MVP (3 агенти + диспетчер) реально можна запустити швидко.

### Ризики і обмеження
1. Додана роль "Psychologist" корисна для manual-трейду, але в автопайплайні може бути суб'єктивною.
2. Якщо робити занадто багато "фондового" формалізму одразу - система стане повільною.
3. Високий ризик розмиття відповідальності між ролями без чіткого протоколу вето.

### Рішення по ідеї
- Статус: **ВЗЯТИ В РОБОТУ (базовий каркас)**.
- Важливість: **дуже висока**, бо ідея дисциплінує саме процес рішень.
- Не беремо в MVP: зайві ролі без вимірюваного ефекту.

### Ядро, яке беремо одразу
1. Бот-стратегія = джерело сигналу (AI не вигадує сигнали).
2. Dispatcher (оркестратор порядку агентів).
3. Analyst (структура/сила сигналу).
4. Risk Manager (RR/exposure/drawdown gate + право вето).
5. Strategist/PM (фінальний ENTER/WAIT/SKIP).
6. Logger (аудит і post-trade аналітика).

### Оновлений пріоритет ролей для твого офісу
1. PM/Strategist (фінальне рішення).
2. Risk Manager (жорсткий контроль ризику).
3. Quant/Analyst (оцінка edge).
4. Dispatcher (координація і таймінг).
5. Logger/Research (накопичення знань і метрик).

### Практичний формат рішення по сигналу
- ENTER (повний розмір)
- ENTER_REDUCED (зменшений ризик)
- WAIT (чекати підтвердження)
- SKIP (пропуск)

### Що додаємо в backlog після цієї ідеї
1. Формальний протокол вето Risk Manager.
2. Єдиний JSON-формат агентських висновків для кожного `signal_id`.
3. Оцінка якості рішень по агентах: `consensus_pnl`, `risk_veto_saved_loss`, `missed_mfe`.

## Аналіз ідеї #3 (Grok) — "AI Trading Desk у Telegram"
Дата: 04.05.2026

### Суть ідеї
- Побудувати окремий Telegram desk-чат, де агенти обговорюють сигнал бота.
- Ролі 6 агентів схожі на фондову команду: coordinator, risk, quant, sentiment, trader, researcher.
- Оркестрація через LangGraph/CrewAI або спрощений aiogram-потік.

### Сильні сторони (беремо в роботу)
1. Практичний формат live-обговорення сигналу (легко читати і контролювати).
2. Хороша думка про staged rollout: почати з простого чату, потім ускладнювати.
3. Правильний акцент на risk-first і позиційному sizing (не лише ENTER/SKIP).
4. Добре підходить для твоєї цілі: "реальний офіс агентів", а не один бот.
5. Корисна ідея окремого журналу дискусії по кожному `signal_id`.

### Ризики і обмеження
1. Якщо всі 6 агентів працюють до входу на кожен скальп-сигнал - буде затримка.
2. "Ray має фінальне слово" без risk-veto може ламати дисципліну ризику.
3. Зовнішні фактори (news/on-chain/funding) не завжди стабільні в real-time і можуть шуміти.

### Рішення по ідеї
- Статус: **ВЗЯТИ В РОБОТУ (частинами)**.
- У MVP до входу запускаємо лише критичні ролі: Analyst + Risk + Strategist/PM.
- Інші ролі (Sentiment/Research/Red Team) підключаємо асинхронно для пост-аналізу і тюнінгу.

### Що беремо одразу в MVP із Grok-ідеї
1. Окремий desk-чат формату "signal room".
2. Координатор (Alice/Dispatcher), який запускає пайплайн і підсумовує.
3. Протокол коротких відповідей агентів із цифрами.
4. Фінальний підсумок у форматі: `ENTER / ENTER_REDUCED / WAIT / SKIP`.
5. Лог по рішенню і аргументах у shared memory.

### Доробка протоколу ролей (важливо)
- Final authority: PM/Strategist.
- Hard veto: Risk Manager (необхідно зафіксувати явно).
- Trader/Executor не змінює risk-ліміти, а виконує рішення.

### Оновлення загального плану офісу
1. Фаза 1: Telegram Desk + Dispatcher + 3 ядрові ролі + logging.
2. Фаза 2: Додати Research/Sentiment/RedTeam як advisor layer.
3. Фаза 3: Mini App dashboard і метрики якості агентів.

- Окремо запропоновано сильну локалізацію (українські імена, стиль "офісної кімнати").

### Сильні сторони (беремо в роботу)
1. Правильний пріоритет risk-правил: hard stop не скасовується ніким.
2. Корисна ідея таблиці `ai_office_performance` для вимірювання ефективності рішень.
3. Добра ідея role-tagging для прозорості, хто саме вплинув на рішення.
4. Практичний фокус на API-стабільності/інфраструктурі (для live-бота це критично).
5. Локалізація українською мовою підвищує читабельність і контроль в Telegram.

### Ризики і суперечності
1. Пропозиція "перехід на SQLite" як єдине сховище може бути вузьким місцем для real-time оркестрації.
2. Занадто багато "персоналізації" (назви/стиль) може відволікти від якості торгових рішень.
3. Твердження про фіксовані сесійні правила типу "до 11:00 найвищий пріоритет" треба валідувати статистикою, не брати як аксіому.

### Рішення по ідеї
- Статус: **ВЗЯТИ ЧАСТКОВО (функціональне ядро + локалізація)**.
- Беремо:
  - risk supremacy (hard-stop недоторканний),
  - performance таблицю по агентських внесках,
  - role tags і прозорий audit trail,
  - україномовний протокол повідомлень.
- Не беремо в MVP:
  - важкий рефактор storage "тільки SQLite" без потреби,
  - нефункціональний брендинг як пріоритет над risk/latency.

### Адаптація під наш офіс
1. Основний state execution лишаємо стабільним у поточному боті.
2. Для AI-office додаємо окремий шар пам'яті рішень (спочатку SQLite, далі при рості - Redis/Postgres).
3. Кожне рішення по сигналу отримує:
   - `signal_id`,
   - `agent_votes`,
   - `final_decision`,
   - `risk_veto_flag`,
   - `post_trade_outcome`.

### Що додаємо в backlog після Gemini
1. Специфікація таблиці `ai_office_performance` (поля + метрики).
2. Формат тегів рішень у Telegram (`[RISK_VETO]`, `[CONSENSUS_GO]`, `[SMC_REVIEW]`).
3. Політика "локалізація без шуму": короткі україномовні повідомлення, без зайвого roleplay.

## Аналіз ідеї #5 (Claude) — "Trading Room як жива кімната агентів"
Дата: 04.05.2026

### Суть ідеї
- Створити окремий файл `trading_room.py` і окремий чат "Trading Room".
- Ввести 5 агентів із ролями, функцією `agent_say(...)`, сценаріями обговорення сигналу, ранковою нарадою, реакцією на закриття угод.
- Інтегрувати в поточний бот через окремий прапорець (`ENABLED`) без поломки основної торгівлі.

### Сильні сторони (беремо в роботу)
1. Дуже правильний підхід "окремий модуль" - мінімальний ризик для ядра.
2. Правильний feature-flag підхід (`ENABLED`) - можна вмикати/вимикати без ризику.
3. Практичні функції: `discuss_signal`, `morning_briefing`, `trade_closed`.
4. Корисна ідея окремого room-чату: аналітика не зашумлює основний торговий чат.
5. Ясна роль Risk Manager як стоп-кран (цю частину залишаємо пріоритетною).

### Критичні технічні ризики в запропонованому чернетковому коді
1. Є несумісні/помилкові імпорти (`from file_1_py import ...`) - так не працюватиме.
2. Прямі звернення до глобалів бота з зовнішнього модуля без ін'єкції контексту дадуть runtime-помилки.
3. Блокуючі `sleep`-затримки у великій кількості можуть створити чергу повідомлень під навантаженням.
4. Форматування і markdown потрібно уніфікувати, інакше буде багато Telegram parse-error.
5. Не можна, щоб room-логіка хоч якось затримувала execution-контур.

### Рішення по ідеї
- Статус: **ВЗЯТИ В РОБОТУ (MVP-архітектуру), код переписати безпечніше**.
- Відкладаємо "великий сценарний roleplay" до стабільного базового MVP.

### Що беремо в MVP прямо з цієї ідеї
1. Файл `trading_room.py` як окремий модуль.
2. `AGENTS` словник (імена/ролі/емодзі).
3. `agent_say(...)` як уніфікований sender.
4. 3 ключові сценарії:
   - `trading_room_discuss_signal(...)`,
   - `trading_room_trade_closed(...)`,
   - `trading_room_morning_briefing(...)`.
5. Конфіги-прапорці:
   - `TRADING_ROOM_ENABLED`,
   - `TRADING_ROOM_CHAT_ID`.

### Що обов'язково змінити перед реалізацією
1. Передавати всі потрібні дані у функції явно (без імпорту глобалів з головного файлу).
2. Зробити неблокуючі, короткі затримки і rate-limit для room-повідомлень.
3. Всі помилки room-модуля ковтати локально, щоб не падала торгова логіка.
4. Зберігати room-історію тільки як sidecar-журнал, не як єдине джерело правди для execution.

### Оновлений пріоритет після Claude-ідеї
1. В першу чергу - безпечний модуль `trading_room.py` з feature flag.
2. Потім - підключення до сигналу/закриття угоди як async side tasks.
3. Потім - розширення до "живого офісу" з додатковими сценаріями.

## Обов'язковий блок офісу 24/7 (додано 04.05.2026)

### 1) Інструкції (логіка агента = "мозок")
- Кожен агент має мати чітку системну інструкцію як для нового співробітника.
- Інструкції повинні містити:
  - межі відповідальності,
  - дозволені дії,
  - заборонені дії,
  - формат відповіді,
  - порядок ескалації.
- Ціль: стабільна поведінка, мінімум "галюцинацій", повторювані рішення.

### 2) Knowledge Base (джерело рішень)
- Агент не "фантазує", а працює тільки від перевірених даних.
- Джерела знань для офісу:
  - поточний стан бота (активні угоди, ризики, ліміти),
  - ринкові дані (ціна, обсяг, спред, funding, сесія),
  - історія угод і рішень агентів,
  - правила офісу (risk policy, session policy).
- Для кожного рішення має бути посилання на факт/метрику, а не "загальна думка".

### 3) Triggers (коли агент стартує дію)
- Тригер - це конкретна подія, яка запускає роботу агента.
- Базові тригери:
  1. `NEW_SIGNAL` (новий сигнал від сканера),
  2. `ENTRY_CONFIRMED`,
  3. `ADD_ZONE_TOUCHED`,
  4. `TP_HIT` (TP1/TP2/TP3),
  5. `SL_HIT` / `BE_HIT`,
  6. `MARKET_REGIME_CHANGED`,
  7. `RISK_ALERT` (серія SL, ліміт збитку, кореляція),
  8. `SESSION_SWITCH` (Asia/London/NY),
  9. `HEARTBEAT_24_7`.

### 4) Постійне ведення відкритих позицій (24/7 on-duty)
- Агенти повинні бути "на зміні" постійно, не тільки в момент нового сигналу.
- Мінімальний цикл супроводу:
  - перевірка відкритих позицій за таймером,
  - переоцінка ризику при зміні ринку,
  - підказка по закриттю/частковій фіксації/добору,
  - логування кожної дії.
- Важливо: офісний моніторинг не блокує основний execution-модуль.

### 5) Пріоритет дій під час live-ринку
1. Захист капіталу (Risk first).
2. Супровід відкритих позицій (не залишати без контролю).
3. Нові входи тільки після перевірки тригерів і правил.
4. Післядія: записати висновок і оновити Knowledge Base.

### 6) Що це означає для реалізації
- Потрібні окремі "черги подій" (event bus) для агентів.
- Потрібен `heartbeat`-процес офісу 24/7.
- Потрібен єдиний формат події: `event_type`, `signal_id`, `payload`, `priority`, `ts`.
- Потрібні правила SLA:
  - реакція на критичні події (SL/RISK_ALERT) - миттєво,
  - реакція на аналітичні події - асинхронно.
