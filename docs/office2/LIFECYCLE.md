# Життєвий цикл сигналів Office2 (14.10.2026)

Принцип: один торговий задум — одна зрозуміла історія. Новий номер — лише для справді нової торгової можливості. Торгові правила Brain, рівні, SL/TP, ризик-обмеження **не змінюються**.

## Сутності
| Сутність | Що це |
|---|---|
| Сценарій | доставлений READY: scenario_id, №, повідомлення Telegram, заморожений план |
| Сетап | теза Brain; `thesis.id` — стабільний id ідеї по монеті (однаковий id = та сама ідея) |
| Подія супроводу | ENTRY / TP1–TP3 / SL … (`office_events`, SCENARIO_MILESTONE) — торкання ціни, не виконання ордера |
| ПРОДОВЖЕННЯ | новий сетап того ж напряму, поки попередній сценарій ще в роботі (немає SL/TP3/EXPIRED/INVALIDATED, не старший за 48 год) |
| ПОВТОРНИЙ ВХІД | новий підтверджений сетап після того, як попередній сценарій завершився |

## Поведінка (`OFFICE2_LIFECYCLE`, за замовчуванням `merge`)
* **ПРОДОВЖЕННЯ**: нового READY немає; подія «СУПРОВІД СЦЕНАРІЮ №N · Продовження руху» — відповіддю на повідомлення початкового READY, один раз на пару (початковий сценарій, id ідеї). Початкові TP1–TP3 показані без змін; «Нова запропонована ціль» — завжди «Потребує підтвердження» (TP4/TP5 і зміну стопа автоматично не додаємо — окрема логіка супроводу, спершу перевірка на історії); реальний рівень за початковими цілями лише як інформація; новий стоп — «Не визначено». Часткових фіксацій, пересування стопа чи прибутку не вигадуємо. Той самий id ідеї, що вже в роботі, — без повідомлення (як раніше було NO_TRADE).
* **ПОВТОРНИЙ ВХІД**: окремий №, рядок «↻ ПОВТОРНИЙ ВХІД · після №N (SL/TP3/…)», відповідь на повідомлення попереднього сценарію, зв'язок у знімку (`thesis.lifecycle`).
* Ризик-обмеження (`portfolio_gate`: ємність, кластер, ≤3 однонапрямлених альти, ліміт за добу) лишаються і застосовуються до повторного входу.
* `annotate` — READY як раніше, лише позначка в знімку; `off` — стара поведінка. Відкат: `OFFICE2_LIFECYCLE=off`.

## Атомарність
Подія створюється `INSERT … ON CONFLICT DO NOTHING` за ключем (початковий сценарій, id ідеї); відправка — через `claim` (UPDATE … WHERE tg_status='NEW' AND claim IS NULL/застарілий) і `send_proactive` з `canonical_id`; збій Telegram → до 3 повторів, далі FAILED.

## Нумерація
Показ: №1, №2, №3 … (без нулів). Внутрішні `scenario_id`, `office_ready_seq`, повідомлення й журнали не змінено.

## Відомі обмеження
* Параметр «не старший за 48 год» = вікно `opposite_lifecycle`; трекер супроводу тримає сценарій до 72 год.
* У Mini App зв'язок продовження/повторного входу показується через знімок і журнал подій; окремого вигляду «історія задуму» ще немає.
