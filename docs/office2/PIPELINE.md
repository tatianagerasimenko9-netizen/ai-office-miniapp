# Office 2.0 (shadow): торговий pipeline зверху вниз — задумано / працює / бракує / реалізовано / edge

Статус: **research-only**, production не змінюється й не імпортує `office2/`. Мета — READY як результат аналізу, а не сигнал із красивим поясненням, доданим потім.
Опорна точка (1m replay 1–4.10, 605 вирішених, кластерний ІВ): поточний відбір READY дає TP1-first 27,3% проти геометричної бази 27,9% (надлишок −0,6 п.п., ІВ −5,0…+4,6) — тобто «приблизно випадкова геометрія».

## Протокол оцінки (обов'язковий для кожного етапу)
1. Лише закриті бари на момент рішення; тест усічення даних (`scripts/test_office2.py::test_no_lookahead_truncation`): кандидати на усічених даних = ті самі кандидати на повних (до моменту усічення); TP/рівень «відомі» не пізніше входу.
2. Метрика: **надлишок = факт TP-first − геометрична база r/(r+t)** (24 год, строгий 1m first-touch, стоп раніше цілі в одну хвилину), кластерний бутстреп за (symbol, день); плюс R чистий (комісія 0,10% кола / ризик%).
3. Train = перші 60% діб, test = решта, **test×hold-out** = test на ≈1/3 символів, не використаних під час дизайну. Параметри задані заздалегідь; на test не підбираються.
4. Сіднійний контроль: випадкові входи (SL 2·ATR15, TP 3·ATR15) мають давати надлишок ≈0 — перевіряє симулятор і базу (на синтетичному блуканні −0,5 п.п., ІВ містить 0).
5. Етап приймається лише якщо його надлишок/R додатний і стабільний на train **і** test (ІВ test не містить 0 у хибний бік); інакше етап лишається декоративним і не отримує вагу.
Застереження про базу: r/(r+t) припускає відсутність дрейфу; на сильно трендових (синтетичних) даних будь-яка напрямково-нейтральна суміш дає «надлишок» через нелінійність (Jensen) — тому контроль і ІВ обов'язкові.
