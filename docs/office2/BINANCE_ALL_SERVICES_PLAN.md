## Що робить AI Office (PR #259, без зміни торгових правил)
1. Один запит на символ за прохід (tick, false-expiry, milestones).
2. Поважає Retry-After (стеля 1800 с), після паузи — один пробний запит, серія 429 подвоює очікування.
3. Супровід не залежить від одного каналу: REST → (за потреби) WebSocket-облік TP/SL для сценаріїв із записаним ENTRY → перерахунок за свічками після зняття бану з фактичним часом події. Дублів немає.
4. Heartbeat і попередження «Супровід застарів» у Mini App; нові READY за застарілими свічками не створюються.
Вимір ефекту: лічильник `klines_callers['15m|office_signal_track.py:tick']` у `[data] binance` — очікується ≈148 на бар замість 1725.

## Що потрібно в scanner-bot (код мені недоступний — репозиторій не підключений до сесії)
Без вимкнення сигналів і Telegram. Патч-специфікація:
1. **Не робити REST під час бану.** Розібрати `banned until <ms>` з APIError(-1003), зберегти як `ban_until` і до цього часу не викликати REST (зараз ≈2 запити/с під час бану). Усі виклики через одну функцію-обгортку.
2. **Один пробний запит** після `ban_until`, решта чекають; при новому -1003 — експоненційна пауза.
3. **WebSocket замість опитування** там, де достатньо: kline-потоки `<symbol>@kline_15m` (сам Binance радить це в тексті помилки), `!miniTicker@arr` для цін; REST — лише для початкового завантаження історії.
4. **Кеш свічок** на 15m-бар: один запит на символ на бар; пакетні/ліміт-обмежені запити (limit мінімальний для задачі).
5. **Деградація без втрати сигналів:** якщо дані недоступні — не надсилати хибний сигнал, а зафіксувати «немає даних» і повторити після `ban_until`; вже відкриті сигнали супроводжувати з кешу/WS.
6. **Розкладання по часу:** запуск повного скану не одночасно з etalon і Office (зсув хвилин).
Те саме правило для binance-scanner-etalon (поки помилок не видно — лише захисна обгортка).

## Варіанти інфраструктури (лише довідка, нічого не запущено; ціни ПРИБЛИЗНІ, не перевірені)
| Варіант | Ефект | Вартість | Ризики |
|---|---|---|---|
| Нічого не купувати: зменшити REST (пункти вище) | Найімовірніше достатньо, якщо навантаження — головна причина | 0 | Потребує змін у коді scanner-bot |
| Інший регіон Render для частини сервісів (напр. Singapore) | Інші вихідні IP → незалежні ліміти | Потенційно 0 за тим самим планом | Перенос сервісу, затримка, перевірити, що Binance не відхиляє регіон; США-регіони для Binance ризиковані |
| Окремий вихідний проксі/статична IP (add-on або невеликий VPS) | Власна IP на сервіс | Невелика щомісячна плата | Нова точка відмови, налаштування |
| Спільний регулятор частоти (Redis/Key Value Render) для всіх сервісів | Єдиний бюджет ваги й спільний `ban_until` | Платний інстанс Key Value | Складніше; не знадобиться, якщо навантаження зменшено |
Рекомендація: спершу пункти 1–5 і підтвердження IP; платне — лише після вашої згоди.
