## Робочий порядок (не 20 маленьких PR)
1. **Live diagnostic:** проаналізуй Scanner→Brain→radar→Postgres→Telegram→Mini App→paper→postmortem; зафіксуй реальні SHA, health, останні успішні події й затримки, наявність нового READY і причини тиші.
2. **Докази джерел:** застосуй правила `SOURCE_GOVERNANCE`. Зв'яжи кожне реалізоване авторське правило із конкретним файлом та кадром/сторінкою. Для архіву не вигадуй timestamp завантаження, класифікуй за коментарями власниці та видимими доказами.
3. **Карта стратегій:** незалежні моделі за фактично підтвердженими матеріалами: Дарія (рівні, пробої, хибні пробої, підтиснення, слабкий відкат, сильна старша свічка/повернення, старший Fibonacci і молодший trigger), Герчик (рівні), SMC/ICT (структура/ліквідність), окремі Wyckoff/Elliott/Bulkowski/paranormal-bar лише за точними доступними джерелами. Ні загальних вигаданих порогів, ні сумування всіх індикаторів.
4. **Логіка TF:** D1/H4 = контекст, сильна свічка та підтверджений старший імпульс/Fibo; H4/H1 = структура й зони; M15 = відкат/перевірка; M5/M1 = точка входу після завершених свічок. Відкладений тригер, invalidation, часові межі, ніякого future leak. Немає доказу — WATCH, не READY.
5. **Сценарні правила:** окремо перевір підтверджені відкотні, пробійні, хибнопробійні та sweep/retest-сценарії; кожен має as-of snapshot, source refs, структурний SL, TP до справжніх рівнів, умову відміни; не перераховуй старий entry/SL постфактум.
6. **Ризик:** якщо всі варіанти стопа не пройшли перевірки, не підвищуй навчальний сценарій до дозволеного сигналу. LIVE gates/3 SL не змінювати, реальних ордерів не вмикати.
7. **Paper:** перевір вхід тільки після події/доставки, NO_ENTRY/MISSED, TP1/SL first, partial exits лише за підтвердженою політикою, fees/slippage, change-of-state alerts, after-stop, postmortem; BTW SHORT використовуй ТІЛЬКИ як UX-референс часткового супроводу — **не копіюй −3,8%, +3%, +5%, +7%, +9,4% у правила**.
8. **Коротка одна картка:** монета/напрям/статус; «План і причини» 1–5 реальних аргументів; «Чекаємо», ціни входу/стопа/TP, скасування; кнопка «Відкрити графік» на **конкретну** картку; не переповнюй фото-підпис, не дублюй старі пости і не генеруй нове сповіщення на кожну 1m/5m свічку.
9. **Mini App:** той самий серверний список аргументів, докази старшого контексту, ref для свічок і рівнів, часові мітки, три альтернативні стопи (оцінка й позначка backfill, якщо є), історія супроводу; спільний Postgres для worker/web; працюючий Telegram deep link.
10. **QA:** replay на історичних Binance 1m/5m/15m/1h/4h/1d без lookahead + зміни ризику, unit/integration, mobile URL; перевіряй міграції, відновлення, rate limits/429, ідемпотентність, відсутність спаму.
11. **Результат моделей:** по версіях, net R, sample size, невизначеність, порівняння незалежних відрізків. 37 попередніх READY із майже нульовим R не доводять позитивного edge; не перебирати фільтри до отримання потрібної статистики.
12. **Порядок впровадження:** об'єднані логічні PR → CI green → merge → обидва Render live на тому самому SHA → вибірка свіжих PG подій, реальна картка, button, paper update, postmortem, захист від дублів. Для події, якої ринок не дав, `WAITING_FOR_MARKET`, контрольовані fixtures окремо.
13. **Фінальний приймальний звіт:** production SHA; доступність API/DB/Binance; конкретний card ID із latest evidence; надісланий Telegram msg id / timing; пряма картка Mini App; paper результат або очікуваний етап; доказ розрахунків трьох стопів; 3 реальні картки з 1–5 причинами; інвентар реально імпортованих джерел, мапа source→rule→code→test, чіткий список SOURCE_MISSING; непідтверджені перевірки. Не писати «повністю запущено», поки E2E не доведено.
