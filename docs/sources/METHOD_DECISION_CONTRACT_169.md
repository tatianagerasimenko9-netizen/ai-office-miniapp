# AI Office — контракт інтеграції торгових методик у рішення (issue #169)

Статус: **специфікація для реалізації, не ввімкнений торговий алгоритм**. Не плутати наявність цього документа з впливом правил на READY.

## Джерела правди та порядок пріоритету

1. `docs/sources/evidence.jsonl`: наявний реєстр 82 правил, з полями `rule_id`, `method`, `source_files`, `explicit_conditions`, `missing_parameters`, `implementation_status`, `code_refs`, `tests_required`.
2. `docs/strategies/SOURCE_RULES.md`: правила достовірності й посилань на першоджерела.
3. `docs/sources/DARIA_TOPDOWN_SEQUENCE.md`: підтверджені спостереження vs вимога власниці vs власні гіпотези.
4. `docs/office2/DARIA_ZHDANOVA_METHOD.md` і бібліотечний `Metodyka_Darii_AI_Office.docx` (вторинна консолідація; сирі байти бібліотечного документа не доступні в репозиторії).
5. `docs/office2/READINESS_2026-10-12.md`: встановлена розбіжність між методиками і чинними READY-гейтами.

**Не дублювати 82 правила вручну**: побудувати машинний індекс безпосередньо з `evidence.jsonl`, зберігаючи первинні ID та provenance.

## Потрібна модель торгового мислення (окремо для LONG і SHORT)

1. **Market state:** BTC/ETH контекст, сесія, календар новин (якщо надійне джерело доступне), волатильність, тренд/діапазон.
2. **Top-down location:** D1 → H4 → H1 → M15 → M5 → M1, лише закриті свічки; для кожного ТФ — стан, рівні, структура, timestamp і протиріччя. Не припускати, що всі шість ТФ є дослівною вимогою Дарії: це вимога власниці до продукту.
3. **Сценарій:** продовження, розворот або діапазон; окремо breakout, false breakout, retest, bounce. Вказати, чому альтернативний сценарій відхилено.
4. **Локація/рівні Герчика:** фіксований чи плаваючий рівень, дзеркальний рівень, люфт, реакція ціни, відстань до наступного бар'єра. Не переносити FX-допуски автоматично на крипту.
5. **SMC:** ліквідність, sweep, BOS/MSS, displacement, OB/FVG/OTE, сесійні моделі — з розмежуванням source rule і власних алгоритмічних порогів.
6. **Дарія:** підтиснення біля горизонтального рівня, слабкість відскоку, закриття біля/під рівнем, ближній ретест, «порожнеча» до наступної цілі; точний M5/M1 тригер позначати `UNVERIFIED_SOURCE` до перегляду оригіналів.
7. **Точний вхід:** planned entry/zone, момент підтвердження, SL за структурою, TP1/TP2/TP3 за реальними перешкодами, net R:R після витрат, TTL, умови скасування і протилежний сценарій. Не підставляти вигадані ціни.
8. **Рішення:** `NO_TRADE` / `WATCH` / `WAIT_CONFIRMATION` / `READY` / `INVALIDATED`; кожне рішення має відтворюваний набір фактів і правило переходу. `WATCH` не є торговим сигналом.
9. **Супровід:** Telegram → paper entry → TP/SL/invalidation → повідомлення → журнал → Mini App, ідемпотентність після рестарту.
10. **Навчання:** окремо зберігати факти та наслідки, не змінювати автоматично LIVE-гейти за результатом окремих угод. Порівнювати кандидати/відхилені сигнали з комісіями, slippage, затримкою і без lookahead.

## Інженерні критерії приймання

- Парсер валідовує **всі** записи `evidence.jsonl`, не губить жодного rule_id, перевіряє дублікати, походження та посилання на існуючі файли.
- Звіт покриття: `rule_id → source → implementation function → test → decision_role → live status`; окремо список правил без реалізації. Не заявляти «впроваджено», якщо правило лише показується.
- Модулі для Gerchik / SMC / Daria оцінюють факти окремо, а decision engine пояснює збіги та конфлікти. Пріоритет і конфлікти не приховувати «середнім балом».
- Позитивні, негативні, інвалідаційні та no-lookahead тести для кожного правила, яке пропонується зробити GATE.
- Додати APE, C98, GALA, ZRX як **історичні кейси з неповною доказовою базою**, а не як достовірні прибуткові угоди.
- Перевіряти на повному наборі кандидатів, включно з відхиленими; метрики gross/net, TP-first/SL-first, витрати, latency, періоди ринку; уникати selection bias.
- Поки немає перевірених оригінальних M5/M1 тригерів і позитивної незалежної перевірки, не перемикати `OFFICE2_LTF_MODE` на блокування та не змінювати LIVE-гейти.
- Не вмикати реальні ордери, не послаблювати ліміти ризику. Не збільшувати ресурси Render без погодження.
- Окремо усунути зафіксований Render `oomKilled` Worker (512 MiB): це production-блокер, не частина торгової методики.
