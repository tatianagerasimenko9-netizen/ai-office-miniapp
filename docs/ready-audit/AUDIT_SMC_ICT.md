## Підтверджені факти-проблеми (за кодом)
1. **BOS/CHoCH при невизначеному тренді.** `res["trend"]=None`, якщо два останні свінги не в один бік. Тоді `"bos" if trend == "UP" else "choch"` та аналогічно для DOWN дають **«choch» для будь-якого пробою** (і LONG, і SHORT). Тобто CHoCH може з'явитись там, де «зміни характеру» формально немає (немає тренду, який змінюється).
2. **CHoCH без привʼязки до структури.** Береться «останній свінг» (hi[-1] чи lo[-1]), а не свінг, що створив останній імпульс/відкат. Класичний CHoCH — злам останнього HL (у висхідному) / LH (у низхідному); код цього не розрізняє.
3. **OTE без напрямку ноги.** `dealing_range` бере останній свінг-high і останній свінг-low **незалежно від порядку**. OTE (0,62–0,79 відкату) має сенс лише для ноги, що вже відбулась у бік сценарію (для LONG — low раніше за high). Код порядок не перевіряє, тож `ote` може позначитись на «нозі» протилежного напрямку.
4. **Одне підтвердження достатньо.** Усі теги (sweep, bos, choch, displacement, fvg, ob, breaker, ote) попадають у загальний список LTF-підтверджень рівноправно; будь-яке одне відкриває follow_setup (див. READY_DEPENDENCY_MAP).
5. **Часові вікна короткі:** sweep — 6 свічок (≈1,5 год), BOS/CHoCH/displacement — 4 свічки (1 год), ретест — «старше 3 свічок».

## Що НЕ реалізовано
Break/Mitigation Block окремо, IFVG, Equal-HL як окремі цілі, Judas swing, kill zones як фільтр, SMT, HTF bias (premium/discount на H4/D1), Liquidity runs з цілями. Усе вище — не імітується в інтерфейсі як наявне.
