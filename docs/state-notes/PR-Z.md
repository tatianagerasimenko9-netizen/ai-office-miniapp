# PR-Z — Пачка 6: replay контрольних кейсів на реальних свічках

`office_replay.py`: ядро replay ведення угоди (крок 15 хв, лише закриті свічки, без підглядання), перевірка шлюзу плану (`check_plan`: геометрія, RR після комісій, мінімальна ціль) і вердикт, що перевіряє код: replay виконано на реальних даних; жодна порада не повторилась; немає слів «закрито» без підтвердження виконання; для LSK — план відхилено шлюзом. Кейси — реальні входи власниці з журналу (`JOURNAL_OPEN`, 2026-09-29): AKE, LONGXIA (`龙虾USDT`), LSK, ENA. BTC range — діапазон без угоди, replay ведення не застосовний.

Запуск на production (з цього середовища Binance і сервіс недоступні): `OFFICE_REPLAY_ON_START=1` на worker → через ~2 хв після старту в лог пишуться рядки `[replay] …` (хронологія, MFE/MAE, вердикт по кожному кейсу). Telegram не задіяно. Після зчитування змінну прибрати.

Тест: `scripts/test_replay.py` (синтетичні свічки: ядро, NO_DATA/NOT_FILLED, шлюз LSK, вердикт).

## Джерело свічок (вимога власниці — не їсти ліміт IP)
Свічки replay беруться з архіву data.binance.vision (денні zip 15м; НЕ рахується в ліміт API; 1г і 4г збираються з 15м). В архіві є лише завершені доби — replay кейсів від 2026-09-29 доходить до кінця тієї доби, поточна доба береться, лише коли архів її вже опублікував; відсутні дні названо у звіті. REST fapi — запасний шлях і тільки при `used_weight_1m` < 600 (невідомо = не ризикуємо) з паузою 1 с між запитами; інакше «немає даних» без вигадок.
